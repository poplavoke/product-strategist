# Правила работы с Git

## Начало задачи

1. Обновить сведения о сервере и убедиться, что рабочая копия чистая:

   ```bash
   git fetch origin --prune
   git status
   ```

2. Перейти на `main`, получить изменения без создания лишнего merge-коммита и
   создать отдельную короткоживущую ветку:

   ```bash
   git switch main
   git pull --ff-only
   git switch -c <тип>/<краткое-описание>
   ```

   Допустимые типы веток: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.

3. Не выполнять задачи непосредственно в `main`.

## Подготовка коммита

Перед каждым коммитом проверить рабочее дерево и индекс:

```bash
git status
git diff
git diff --cached
```

Добавлять файлы и фрагменты осознанно:

```bash
git add <файл>
git add -p
```

Коммит должен содержать одно логически завершённое изменение. Исправление,
новая функция, форматирование и документация по возможности оформляются
отдельными коммитами.

Сообщение коммита имеет формат:

```text
тип(область): описание
```

Допустимые типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.
Заголовок должен быть не длиннее примерно 72 символов, начинаться со строчной
буквы, не завершаться точкой и содержать глагол в повелительном наклонении.

Примеры:

```text
feat(research): добавить реестр источников
fix(strategy): исправить проверку обязательных разделов
docs(git): описать процесс ревью
chore(ci): добавить проверку markdown
```

## Безопасность

- Не использовать `git restore`, `git reset --hard` и `git clean` без проверки
  последствий. Перед очисткой всегда выполнять `git clean -n`.
- Не переписывать опубликованную историю. Общие коммиты отменять через
  `git revert`.
- `git stash` использовать только для кратковременного сохранения работы.
- Не добавлять секреты, закрытые ключи, токены, логи, датасеты, веса моделей и
  генерируемые артефакты. Файл `.gitignore` не прекращает отслеживание уже
  добавленного файла; для этого применяется `git rm --cached <файл>`.
- Не передавать закрытые SSH-ключи и не помещать токены в URL репозитория.
- Файлы больше 5 МиБ требуют отдельного обоснования и подходящего хранилища;
  для версионируемых крупных файлов использовать Git LFS.

## Pull Request и ревью

1. Отправить рабочую ветку и открыть небольшой Pull Request в `main`.
2. В описании указать, что и зачем изменено, как проверить результат и какие
   риски остаются.
3. Дождаться успешных автоматических проверок и одобрения ревьюера.
4. На каждое замечание ответить исправлением или аргументированным объяснением.
   Исправления добавлять новыми коммитами в ту же ветку.
5. После обработки замечания закрыть соответствующее обсуждение.
6. После слияния удалить ветку на сервере и локально:

   ```bash
   git switch main
   git pull --ff-only
   git branch -d <имя-ветки>
   ```

Комментарии ревью должны относиться к коду и техническому решению, а не к
личности автора.

## Конфликты и неуспешные проверки

При конфликте определить правильное итоговое содержимое, удалить служебные
маркеры конфликта, выполнить `git add` и завершить слияние. Состояние конфликта
проверять через `git status`; ненужное слияние отменять командой
`git merge --abort`.

Если CI завершился ошибкой, изучить лог, воспроизвести проблему, исправить её и
отправить новый коммит. Не обходить проверки через `--no-verify` и не
перезаписывать чужие изменения с помощью `push --force`.
